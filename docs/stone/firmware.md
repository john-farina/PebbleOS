# Firmware changes

Everything the fork adds to the firmware is behind `CONFIG_STONE`, a bool in
`Kconfig.stone` defaulting to `y`. Turning it off builds functionally-upstream
firmware, which is the cheap way to bisect a bug against stock behaviour without
unwinding the patch queue.

`Kconfig.stone` is sourced by one `rsource` line at the foot of the root
`Kconfig`.

## What is changed, and where

| Area | Files | |
| --- | --- | --- |
| Boot splash | `src/fw/board/splash/splash_stone.xbm`, `splash.h` | A `stoneOS` wordmark |
| Build metadata | `src/fw/stone_build_info.auto.h.in`, `tools/stone/build_info.py` | Branch, commit, base, dirty, and on a WIP branch the build label and summary |
| Stone app | `src/fw/apps/system/stone_app.{c,h}`, `settings/stone.{c,h}`, `launcher/default/app_glance_stone.{c,h}` | The build the watch is running, first in the app list |
| Rebrand | 11 source files | One user-visible string each |

## The boot splash

The splash is a **112×29, 1-bit bitmap** — a wordmark, not a logo mark.
`splash.h` selects `splash_stone.xbm` ahead of the per-board chain when
`CONFIG_STONE` is set, so every board gets it.

The bitmap is **generated from an SVG**, not hand-plotted: render at 112×29 and
threshold to 1-bit. It can be redrawn by editing vectors rather than picking
pixels.

One gotcha if you regenerate it: **Chromium refuses to lay out a 112×29
viewport** and silently screenshots blank. Render at a larger window size and
crop the top-left corner, which is still a 1:1 pixel grid.

## Build metadata

`git describe` records the nearest tag and the commit but **not the branch**,
and `version_tag` is 32 bytes with no room to carry one. With several WIP builds
in flight the branch is exactly what you need, so it comes from a generated
header instead:

```c
#define STONE_BRANCH "stone"
#define STONE_COMMIT "97945fe"
#define STONE_BASE   "v4.36.0"
#define STONE_DIRTY  0
```

Generated by `tools/stone/build_info.py` via a custom command in
`src/fw/CMakeLists.txt`, modelled on the identical `git_version.auto.h` block
beside it. `pbl_include_directories(.)` puts the binary directory on the global
interface, so `#include "stone_build_info.auto.h"` resolves from anywhere in
`src/fw/`.

**Deliberately no build timestamp.** The header is rewritten only when its
contents change; a wall-clock would change every invocation and force a full
rebuild each time.

## Settings → Stone

`src/fw/apps/system/settings/stone.c` shows branch, commit, upstream base,
firmware version and the active slot. Slot is not cosmetic: an update writes
into the *other* slot, so it tells you where the next install lands.

### Adding a settings category

The settings sources are picked up by `file(GLOB_RECURSE source ... *.c)` in
`src/fw/apps/system/CMakeLists.txt`, so **a new module needs no build change**.
Three guarded one-liners wire it in:

1. `settings/menu.h` — a `SettingsMenuItem…` enum entry
2. `settings/menu.c` — a `s_submodule_registry` entry, plus the include
3. `settings/settings.c` — an icon in `SETTINGS_MENU_ICON_RESOURCES`

Then implement `SettingsCallbacks` and return
`settings_window_create(category, &data->callbacks)` from your `init`.

Two things worth knowing before you copy an existing module:

- **Grep for every table indexed by the enum** before adding a category. There
  are two arrays sized by `SettingsMenuItem_Count` in `settings.c`; missing one
  is a null dereference when the menu builds, not a compile error.
- **The module owns its allocation.** `settings_window_destroy` calls your
  `deinit` and then frees only *its* data. `timeline.c` does `i18n_free_all`
  **and** `app_free`; `system.c` omits the `app_free` and appears to leak.
  Follow `timeline.c`.

Reusing an existing icon resource avoids touching the resource manifest.

## The rebrand strings

Eleven `i18n_noop` / `i18n_get` strings name Pebble where the wearer reads them.
Strings about the phone became "Stone app"; strings meaning the hardware became
**"your watch"**, which reads better than either brand name.

Changing an `i18n_noop` msgid **drops that string's existing translations back
to English**. With eleven strings and English-only use that is the right trade,
but it is a real cost worth restating before adding more.

## Versions

Fork builds describe as `v<base>-<n>-g<sha>`, for example
`v4.35.0-126-gf33a5d751`. Three different parsers see that string, and a tag
that breaks any of them breaks something:

| Parser | Where | Cares about |
| --- | --- | --- |
| `tools/gitinfo.py` | firmware build | **Raises on a tag it cannot parse**, failing the build |
| `tools/pblboot.py` | boot priority | Exact `vX.Y.Z` = release band; anything else = dev band |
| `libpebble3` | companion app | `v?(\d+)\.(\d+)(?:\.(\d+))?(?:-(.*))?`, ordered on the first three only |

Consequences:

- **Any tag reachable from `stone` must be version-shaped.** A tag like
  `safe-2026-08-31` would fail *every* later build, because `git describe` finds
  the nearest reachable tag. Safe builds use `vX.Y.Z-safeN` for this reason.
- **A fourth version component is invisible to the app.** Do not use
  `v4.36.2.1`; put the discriminator in the suffix.
- **Every fork build lands in the bootloader's dev band**, since none of our
  tags are an exact `vX.Y.Z`. Within that band the **most recently built** image
  wins — not the most recently installed. See {doc}`recovery`.
